# Самостоятельная установка Nimbo — предварительный пакет

Это установщик серверной части для Linux amd64. Он поднимает API Nimbo, LiveKit и Caddy, без Grafana, общей авторизации и сервисов разработчика. Выполняется из распакованного пакета с `nimbo-server`, `SHA256SUMS`, `install.py`, `nimbo`, `Dockerfile.binary`. Готового публичного релиза и URL загрузки пока нет.

Для сборки из исходников с установленными Go, Node и зависимостями `web/node_modules`: `node scripts/package-selfhost.mjs`. Скрипт проверяет типы интерфейса, собирает его и статический Linux-бинарник во временном каталоге под `artifacts/selfhost/`, затем создаёт архив. Рабочие бинарники и `server/ui` не заменяются. Автоматические тестовые наборы эта команда не запускает.

## Чистый сервер

Нужны Python 3, Docker Engine с Compose v2, публичный IPv4 на интерфейсе сервера и три DNS-имени с A-записями на этот IP. Если есть AAAA-записи, IPv6 тоже должен работать. Серверы за NAT и установка по голому IP пока не поддержаны этим установщиком. На старте ориентируемся на Ubuntu/Debian. Установщик не меняет SSH, firewall, пакетный менеджер и чужие контейнеры.

Из каталога проверенного релизного пакета:

```sh
sudo python3 install.py --domain chat.example.org --rtc-domain rtc.example.org --turn-domain turn.example.org --public-ip 203.0.113.10
```

Адрес и домены выше — примеры, их нужно заменить. При стандартной установке снаружи нужны TCP 80/443/7881 и UDP 7882/3478. API 8090 и сигналинг 7880 слушают loopback; TURN 5349 доступен через TLS-прокси на 443. Не открывайте внутренние порты. Caddy получает и продлевает сертификаты автоматически. Входящий трафик должен доходить до этого VPS; CDN-прокси для медиасервера не подходит.

Установка откажется перезаписывать существующий каталог или проект Compose, проверит DNS и свободные порты. Контрольная сумма проверяет целостность бинарника, но сама по себе **не удостоверяет издателя**: подпись публичных релизов — отдельный этап перед выпуском.

После запуска:

```sh
sudo /opt/nimbo-selfhost/nimbo help
sudo /opt/nimbo-selfhost/nimbo status
sudo /opt/nimbo-selfhost/nimbo owner-code
```

Сначала сервер не имеет владельца и не принимает обычную регистрацию. Последняя команда создаёт случайный одноразовый код на 30 минут. В совместимом клиенте добавьте адрес сервера и используйте код как приглашение. Профиль станет владельцем. Установщик не создаёт профиль за пользователя и не требует заранее поднимать веб-клиент.

Повторная выдача отменяет предыдущий неиспользованный код. После появления владельца команда отказывает, передачей владения она не является. API сохраняет только хеш кода; погашение и назначение владельца выполняются одной операцией записи базы. Команда ненадолго останавливает **только API этой установки**, поскольку JSON-хранилище пока рассчитано на одного писателя. Не запускайте бинарник `owner-code --offline` вручную параллельно API.

По умолчанию HTTPS отдаёт только API и healthcheck. `--web-preview` открывает встроенный веб-клиент для проверки текущей разработки, это не обещание веб-клиента в первом публичном релизе.

## Второй стенд на том же VPS

Используйте другое имя `--project`, новый `--directory` и свободные порты. Это отдельные контейнеры и данные, **не отдельная VM и не защита от root основного VPS**. Docker host network разделяет сеть хоста. Для cookie задаётся отдельное пространство имён, чтобы вход на другом порту не перезаписал cookie рабочего сервера. При реальном разделении доверия нужны отдельные домены: cookie браузера не изолированы портами.

С существующими сертификатами в закрытом каталоге (`app.crt/app.key`, `rtc.crt/rtc.key`, `turn.crt/turn.key`):

```sh
sudo python3 install.py --directory /opt/nimbo-test --project nimbo-test --domain chat.example.org --rtc-domain rtc.example.org --turn-domain turn.example.org --public-ip 203.0.113.10 --https-port 9443 --api-port 18090 --signal-port 17880 --rtc-tcp-port 17881 --rtc-udp-port 17882 --turn-tls-port 15349 --turn-udp-port 13478 --certificate-directory /root/nimbo-test-certificates --web-preview
```

Здесь публичные TCP-порты — 9443, 17881, **15349**, UDP — 17882, 13478. TURN TLS завершается непосредственно в LiveKit на 15349. Сертификаты должны покрывать соответствующие DNS-имена; установщик проверяет имя, срок и соответствие ключа сертификату. Они копируются в закрытый каталог установки. **Копии автоматически не обновляются**: этот режим предназначен для подготовленных сертификатов и временного стенда; обновление сертификатов выполняет администратор.

`--prepare-only` только готовит файлы. Затем выполните `sudo /путь/nimbo install`. Встроенная блокировка CLI защищает от одновременных команд установки/выдачи кода, но не от ручного запуска второго процесса над базой.

## Данные и ограничения предварительного выпуска

- `data/workspace.json` — база, `private/` — секреты. Они не входят в дистрибутив и не должны попадать в Git. Резервное копирование базы выполняйте при остановленном API; защищайте также конфигурацию и сертификаты. Профили `.nimbo` сохраняются пользователями отдельно.
- `nimbo stop` сохраняет данные. Автоматических prune, удаления старых каталогов, миграции действующего сервера или обновления ОС нет.
- Ограничения контейнеров: API 256 МБ, LiveKit 1 ГБ, Caddy 256 МБ; это параметры небольшого стенда, а не обещание ёмкости сервера. Звонки ограничены 10 участниками конфигурацией.
- Проверка `/healthz` подтверждает только API. HTTPS, вход по приглашению, аудио/видео между двумя сетями, TURN fallback, перезапуск и восстановление копии проверяются отдельно перед публичным выпуском.
- Эта сборка **пока не шифрует сообщения сквозным способом**. Проект шифрования: `docs/MESSAGE-ENCRYPTION.md`. TLS защищает транспорт; база текущего формата содержит текст.
- Обновление/откат и подписанная загрузка одной командой ещё не реализованы. Не заменяйте эту установку запуском `install` поверх её каталога.
